# پردازش اسناد (Ingestion) — فارسی

این سند توضیح می‌دهد که `ai-knowledge-service` چگونه یک فایل آپلودشده را به
قطعه‌های (chunk) امبدشدهٔ قابل جستجو تبدیل می‌کند. این مستند دقیقاً
**رفتار پیاده‌سازی‌شدهٔ فعلی** را شرح می‌دهد.

## نمای کلی

```mermaid
flowchart LR
    A[آپلود] --> B[اعتبارسنجی]
    B --> C[حذف تکراریِ فایل]
    C --> D[استخراج متن]
    D --> E[نرمال‌سازی]
    E --> F[حذف تکراریِ محتوا]
    F --> G[قطعه‌بندی]
    G --> H[امبدینگ]
    H --> I[ذخیره‌سازی + فعال‌سازی]
```

مراحل آپلود تا حذف تکراریِ فایل داخل همان درخواست HTTP انجام می‌شوند؛ مراحل
استخراج تا فعال‌سازی در یک **تسک پس‌زمینه** اجرا می‌شوند و درخواست HTTP بلافاصله
پاسخ می‌گیرد. درخواست هرگز به‌خاطر پارس یا امبدینگ بلاک نمی‌شود.

## API

مستندات تعاملی Swagger در مسیر `GET /docs` در دسترس است.

### `POST /documents` — آپلود

- **درخواست**: `multipart/form-data` با یک فیلد `file`.
- **انواع پشتیبانی‌شده** (بر اساس پسوند فایل):

  | پسوند | MIME type ذخیره‌شده |
  |--------|----------------------|
  | `.pdf`  | `application/pdf` |
  | `.docx` | `application/vnd.openxmlformats-officedocument-wordprocessingml.document` |
  | `.xlsx` | `application/vnd.openxmlformats-officedocument.spreadsheetml.sheet` |
  | `.csv`  | `text/csv` |

- **حداکثر حجم**: با `MAX_UPLOAD_MB` (پیش‌فرض ۵۰ مگابایت) کنترل می‌شود و هنگام
  استریم فایل اعمال می‌گردد.
- **پاسخ‌ها**:
  - `202` — پذیرفته شد؛ پردازش در پس‌زمینه شروع شد:

    ```json
    { "document_id": "…", "job_id": "…", "status": "processing" }
    ```

  - `200` — فایل دقیقاً تکراری است (هش SHA-256 یکسان). **پردازش جدیدی اجرا
    نمی‌شود** و سند موجود برگردانده می‌شود:

    ```json
    { "document_id": "…", "status": "active", "deduplicated": true }
    ```

  - `413` — فایل بزرگ‌تر از حد مجاز. `415` — نوع فایل پشتیبانی نمی‌شود.
  - `500` — خطای غیرمنتظره (`{"detail": "Internal server error"}`؛ جزئیات
    فقط در لاگ سرور ثبت می‌شود و به کلاینت برنمی‌گردد).

### `GET /documents/{document_id}` — استعلام وضعیت

پس از آپلود، این endpoint را به‌صورت دوره‌ای (مثلاً هر ۱–۲ ثانیه) صدا بزنید تا
وقتی `status` از حالت `processing` خارج شد.

```json
{
  "id": "…", "name": "report.pdf", "mime_type": "application/pdf",
  "size": 183412, "file_hash": "…", "content_hash": "…",
  "status": "active", "created_at": "…", "updated_at": "…",
  "job_status": "completed", "error_code": null, "error_message": null
}
```

اگر شناسه ناشناخته باشد، `404` برمی‌گردد.

### `GET /documents` — فهرست اسناد

فهرست ادمین، از جدید به قدیم. پارامترها: `limit` (۱ تا ۲۰۰، پیش‌فرض ۵۰) و
`offset` (پیش‌فرض ۰). هر آیتم شامل `status`، `chunk_count`، `usage_count`،
`last_used_at` و زمان‌های ایجاد/به‌روزرسانی است؛ پاسخ شامل `total`، `limit` و
`offset` نیز هست.

### `PATCH /documents/{id}/status` — فعال/غیرفعال‌سازی

بدنه: `{"status": "active"}` یا `{"status": "inactive"}`. فقط همین دو مقدار
پذیرفته می‌شود — `processing` و `failed` متعلق به پایپ‌لاین پردازش است. پاسخ
همان ساختار `GET /documents/{id}` است. `404` برای شناسهٔ ناشناخته؛ `409` در
حین پردازش؛ `422` برای هر مقدار دیگر.

### `GET /documents/{id}/jobs` — تاریخچهٔ جاب‌ها

فهرست جاب‌های پردازش سند، از جدید به قدیم: `status`، `error_code`،
`error_message`، `started_at`، `finished_at`، `created_at`. اگر سند وجود
نداشته باشد `404`.

### `DELETE /documents/{id}` — حذف

در موفقیت `204`. رکورد سند در یک تراکنش واحد حذف می‌شود — قطعه‌ها و جاب‌ها با
`ON DELETE CASCADE` خودکار پاک می‌شوند — و سپس فایل ذخیره‌شده از دیسک حذف
می‌گردد، اما فقط اگر سند دیگری به همان فایل (content-addressed) ارجاع ندهد.
در حین پردازش با `409` رد می‌شود تا جاب پس‌زمینه هرگز بی‌صاحب نماند؛ اگر سند
وجود نداشته باشد `404`.

## مدل وضعیت‌ها

**سند** (`ai_assistant.documents.status`):

| وضعیت | معنی |
|--------|------|
| `processing` | در حال پردازش (هنوز قابل استفاده نیست). |
| `active` | همهٔ قطعه‌ها و امبدینگ‌ها ذخیره شده‌اند — آمادهٔ استفاده. |
| `inactive` | رد شده: سند دیگری با همین محتوای نرمال‌شده وجود دارد. |
| `failed` | پردازش شکست خورد؛ به `error_code` و `error_message` جاب مراجعه کنید. |

**جاب** (`ai_assistant.ingestion_jobs.status`):
`pending → processing → completed | failed`

کدهای خطا (`error_code`): مقدار `corrupt_file` (فایل خراب/غیرقابل پارس)،
`empty_content` (هیچ متن قابل‌استفاده‌ای استخراج نشد)، `config_error`
(مثلاً `OPENAI_API_KEY` تنظیم نشده)، `document_missing`، یا نام کلاس استثنا
برای خطاهای غیرمنتظره. در جاب تکمیل‌شدهٔ تکراری، مقدار `duplicate_content`
به‌عنوان یادداشت غیرخطا در `error_code` ثبت می‌شود.

**تضمین مهم**: درج قطعه‌ها و تغییر وضعیت به `active` در **یک تراکنش
دیتابیسی واحد** انجام می‌شود. پردازش ناقص یا ناموفق هرگز نمی‌تواند سندی را در
وضعیت `active` باقی بگذارد.

## حذف تکراری (دو سطح)

1. **سطح فایل** — SHA-256 بایت‌های خام (`file_hash`، با ایندکس یکتا). آپلود
   دوبارهٔ همان فایل → پاسخ `200` و عدم پردازش مجدد.
2. **سطح محتوا** — SHA-256 متن نرمال‌شدهٔ استخراج‌شده (`content_hash`). فایل‌های
   متفاوت با محتوای یکسان (مثلاً PDF و DOCX از یک متن) → سند جدید `inactive`
   می‌شود و جاب آن با `duplicate_content` تکمیل می‌گردد.

## جزئیات پایپ‌لاین

- **استخراج** (به ازای هر فرمت، به یک ساختار مشترک `Block`):
  PDF ← پاراگراف‌ها با شمارهٔ صفحه (pypdf)؛ DOCX ← سرفصل‌ها (استایل‌های
  `Heading 1–6` و `Title`)، پاراگراف‌ها و جدول‌ها به ترتیب سند (python-docx)؛
  XLSX ← یک بلاک جدول به ازای هر شیت غیرخالی، نام شیت به‌عنوان section
  (openpyxl)؛ CSV ← یک بلاک جدول با تشخیص خودکار delimiter (ماژول استاندارد
  `csv`).
- **نرمال‌سازی** — یونیکد NFC، حذف کاراکترهای کنترلی، ادغام فاصله‌های پیاپی،
  حذف بلاک‌های خالی. این مرحله **قبل از** محاسبهٔ هش محتوا اجرا می‌شود تا تفاوت
 ‌های سطحی فضای خالی باعث شکست حذف تکراری نشوند.
- **قطعه‌بندی** — بلاک‌ها تا سقف `CHUNK_SIZE_CHARS` (پیش‌فرض ۲۰۰۰؛ تقریباً هر
  توکن ۴ کاراکتر) در یک chunk بسته‌بندی می‌شوند و `CHUNK_OVERLAP_CHARS`
  (پیش‌فرض ۲۰۰) کاراکتر از انتهای هر chunk در ابتدای بعدی تکرار می‌شود.
  سرفصل‌ها chunk نمی‌شوند؛ به‌جای آن context بخش بعدی را تشکیل می‌دهند. بلاک‌های
  بزرگ‌تر از سقف، از سر جمله/خط شکسته می‌شوند. هر chunk فیلد `context`
  (`Document: … | Section: … | Page: …`) را جدا از `content` ذخیره می‌کند.
- **امبدینگ** — مدل OpenAI `text-embedding-3-small` (۱۵۳۶ بعد، مطابق ستون
  `VECTOR(1536)`)، در دسته‌های `EMBEDDING_BATCH_SIZE` (پیش‌فرض ۶۴). متن ارسالی
  به مدل ترکیب `context + "\n\n" + content` است.
- **ذخیره‌سازی** — SQL مستقیم با psycopg روی جداول موجود
  `ai_assistant.documents` / `document_chunks` / `ingestion_jobs`. فایل اصلی
  به‌صورت content-addressed (`{file_hash}{ext}`) در `STORAGE_DIR` نگه داشته
  می‌شود تا re-chunk یا re-embed آینده ممکن باشد.

## اجرای ناهمگام و هم‌روندی

پردازش به‌صورت تسک پس‌زمینهٔ درون‌پروسه‌ای اجرا می‌شود (بدون Celery/Redis) و یک
سماфор تعداد جاب‌های هم‌زمان را به `INGESTION_MAX_CONCURRENT` (پیش‌فرض ۲)
محدود می‌کند. فراخوانی پارسرهای بلاک‌کننده در ترد جدا اجرا می‌شود؛ امبدینگ و
کار دیتابیس async هستند. توجه: ری‌استارت سرویس در میانهٔ پردازش، سند را در
وضعیت `processing` رها می‌کند (هرگز `active` نمی‌شود) — برای تلاش مجدد، فایل را
دوباره آپلود کنید.

## مرجع تنظیمات

| متغیر محیطی | پیش‌فرض | کاربرد |
|--------------|---------|--------|
| `MAX_UPLOAD_MB` | 50 | سقف حجم آپلود |
| `STORAGE_DIR` | `data/uploads` | محل نگهداری فایل اصلی |
| `CHUNK_SIZE_CHARS` | 2000 | حداکثر کاراکتر هر chunk |
| `CHUNK_OVERLAP_CHARS` | 200 | هم‌پوشانی بین chunkها |
| `OPENAI_API_KEY` | — | برای امبدینگ الزامی است |
| `OPENAI_BASE_URL` | — | پراکسی/گیت‌وی اختیاری |
| `EMBEDDING_MODEL` | `text-embedding-3-small` | مدل امبدینگ |
| `EMBEDDING_BATCH_SIZE` | 64 | تعداد chunk در هر فراخوان API |
| `INGESTION_MAX_CONCURRENT` | 2 | حداکثر جاب‌های هم‌زمان |
